# 运行维护与综合验证

系统在本机使用 PostgreSQL/PostGIS 和两个受控后台工作进程。普通网页账户与数据库登录账户分开；维护工具通过本机配置连接数据库，备份使用普通应用数据库账户，建立隔离恢复库时才读取数据库管理员凭据。

## 1. 日常启动与停止

在项目根目录运行 `python scripts/run_local.py --port 8000`，或使用已有环境执行 `scripts/start_local.ps1`。启动器同时管理网页、导入和分析工作进程；分析进程处理风险、预测、报告、导出与简报。浏览器访问 `http://127.0.0.1:8000/`。

结束时执行 `python scripts/run_local.py --stop --port 8000` 或 `scripts/stop_local.ps1`。启动器只停止自己持有的进程，不停止共享 PostgreSQL。数据库服务单独由本机管理员管理。仅启动网页不会自动执行排队任务；后台状态、进度和失败原因在对应任务页面显示。

## 2. 完整维护备份

先结束后台任务并停止本机网页服务，然后使用有运行维护权限的应用账户标记操作归属：

```powershell
python scripts/maintain_local.py backup --actor <应用管理员用户名> --tools-dir '<PostgreSQL程序目录>/bin'
```

备份建立不可变的维护记录，并使用一致的数据库事务快照执行 `pg_dump`；逐表记录数量、关系、空间检查及月度统计与该快照对应。文件先建立清单，再核对写入前后的内容。工具拒绝正在运行的受管服务和待处理数据任务，不强制停止其他进程。

| 材料 | 备份方式 |
|---|---|
| 业务、空间、来源、审计、账户、历史分析／报告／简报 | `database.dump`，PostgreSQL 自定义格式 |
| 原始快照、上传文件、来源清单、完成导出附件 | `files.zip`，保留相对目录 |
| 核对口径、逐表数量、代表性统计、内部文件校验值 | `manifest.json` |
| 维护完成结果 | 数据库维护记录与 `receipt.json` |
| 本机 `.env`、密码文件、模型私有配置 | 不自动复制，另行私有保管 |
| 源码、依赖与迁移 | 使用对应版本的源码材料，维护包不替代源码归档 |
| 运行令牌、临时日志、开发证据及其他备份 | 不进入本次文件包 |

结果位于 `var/backups/<维护编号>/`，不同操作不覆盖已有目录。数据库中包含应用密码哈希、会话和审计信息，维护包仍应私有保存，不能因没有明文 Key 就公开发布。文件完整性校验值仅用于维护核对，不作为报告页面内容。

## 3. 实际隔离恢复

只接受本工具已经完成并验证的维护备份编号；工具核对清单与归档完整性后才恢复。目标必须是从未存在、以 `restore_nk_traffic_` 开头的本机验证库，禁止使用业务库、测试库、系统库或连接字符串。

```powershell
python scripts/maintain_local.py restore --actor <应用管理员用户名> --backup-id <备份编号> --target restore_nk_traffic_example --tools-dir '<PostgreSQL程序目录>/bin' --admin-password-file '<私有管理员密码文件>'
```

恢复创建新库，使用 `pg_restore --exit-on-error --jobs=2` 重建归档中的结构、数据和原对象归属；不会执行针对现有项目库的清空或覆盖。完成后核对每张表数量、月份事故／伤亡汇总、修订水位、人员—车辆关系、几何／SRID、约束和索引有效性、PostGIS 距离函数，再将文件恢复到独立目录并逐项核验。

备份必然在自己的完成时刻之前捕获维护记录，恢复工具只会根据已验证回执补记该条备份的完成状态，不改写原始业务事实。失败的新库或目录保留供核查，不能作为已验证副本启动；原库和原文件保持不变。已有目标不支持强制覆盖重试，应核查原因并使用新的隔离目标。

`--actor` 表示可信本地维护命令的操作归属，同时检查该账户的运行维护权限；它不代替操作系统对本机配置及管理员密码文件的访问控制。网页不提供任意 SQL 或系统命令执行入口。

命令语义依据 [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)和 [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)。自定义归档目录可读与实际恢复成功分别记录，不能混称。

## 4. 在恢复副本中启动应用

```powershell
python scripts/run_local.py --restore-run <通过验证的恢复编号> --port 8000
```

使用项目 PowerShell 脚本时，可执行 `scripts/start_acceptance.ps1 -RestoreRun <恢复编号>`。启动器核对恢复记录、数据库标记和文件目录，再一起选择目标数据库和独立存储。代码、前端资源及私有运行配置沿用本机工程，数据库写入、上传和导出使用副本；页面显示隔离提示。不要仅手改数据库名却继续使用原文件目录。

停止方式与普通服务相同。此入口用于验证或人工测试，不能将副本修改误认为已合并到主业务库。数据库恢复验证的记录保存在发起操作的主库，副本只继承备份时已有的历史。

## 5. 失败与维护边界

- 数据库连接不可用时返回清晰的服务提示，不向页面输出连接字符串或调用堆栈。诊断时先查看本机服务和连接配置，不为验证失败而停止可能共享的数据库实例。
- 导入校验与入库分开；重复、内容冲突和格式错误分别记录。中断任务重新启动后有明确失败／可重试状态，重试不覆盖原始证据。
- 风险、预测和报告按生成时的版本保留，数据修订后缓存失效和旧计算提示分别处理；旧报告保持冻结结果。
- 模型不可用时普通统计、报告与已有简报可继续使用。模型输出可能不满足校验，允许受限重试，失败不记作成功。AI 文字的含义仍需要人工核查。
- 删除旧备份、隔离数据库或文件副本前，应核对名称、用途、引用和保留需要。当前工具刻意不提供任意覆盖已有库的参数。

## 6. 已执行的技术验证

完整数据上的技术验证覆盖跨模块修订、缓存、历史结果、权限与参数边界，以及文件备份和隔离恢复。自动化回归共 220 项通过，系统及迁移检查正常。项目现有 46 张业务／管理表，另有 9 张 Django 认证、会话和迁移基础表；恢复逐表核对共 55 张表。第一次完整维护包有 234 个来源文件与附件，首次完整恢复及独立人工验收副本恢复均已实际核对。收尾包增加一个合法导出附件，共 235 文件，其归档验证单独记录。

性能测量使用同一台本机、同一正式快照；重复读取三次，保留每次与中位数。示例数据量为事故 487,914、人员 1,697,877、采样观测 424,268。以下为后端操作耗时，不等同于浏览器完整响应或并发服务承诺：

|---|---|---|
| 全量官方人员计数 | 299.16 / 274.69 / 273.80 ms | 1,697,877 条 |
| 皇后区 2025 年 1 月、关联 Sedan 事故筛选及第一页 | 300.87 / 130.36 / 143.40 ms | 关联条件使用存在性筛选 |
| 曼哈顿局部视野、2025 年地图查询 | 806.87 / 240.48 / 243.70 ms | 包括聚合及当前列表 |

技术验证与人工验收分别记录；当前阶段不据自动化结果宣称用户已经确认最终版本。
