# 城市道路交通数据库应用系统详细设计

版本：1.7；日期：2026-10-06。业务地域为纽约市五区，课程分析快照为 2021—2025 年。日期范围由数据及筛选配置决定，不写入不可更改的业务常量。

本文给出全系统逻辑设计，并明确已落实的物理结构与需要随功能补充的结构。完整字段表见[数据字典](数据字典.md)，界面约定见[界面规范](界面规范.md)，图形见[设计图索引](diagrams/图示说明.md)。未来模块的逻辑设计不代表功能已经运行。

## 1. 用户流程与职责

| 使用者 | 操作链 | 关键边界 |
|---|---|---|
| 系统管理员 | 登录 → 来源及批次核对 → 账户授权 → 日志核查 → 备份与隔离恢复 | 普通 Web 会话不使用 PostgreSQL 超级用户；覆盖已有业务库须另行确认 |
| 数据维护人员 | 登录 → 查看原始来源 → 提交导入 → 查看质量问题 → 说明依据并修正 → 核对关联与日志 | 原始证据不可改写；维护、修正及日志在明确事务边界内处理 |
| 分析用户 | 登录 → 设置时间与区域 → 检索/地图 → 统计与风险 → 预测回测 → 保存条件 → 报告/简报 | 只使用已发布且符合统计规则的记录；不修改事故事实 |

事故详情可回到来源，并展开车辆及人员；车辆/人员也可回到事故。统计下钻必须使用相同筛选条件及统计单位。流量页面按采样请求、地点、方向和当地时间查询，不把采样地点命名为永久在线设备。无坐标事故仍可进入时间及伤亡统计。

已落实页面包含登录及权限、业务档案维护、质量核查、后台文件任务、来源与审计，以及道路地图、道路／路口管理、空间关联核查和采样流量分析。重型全量匹配由可恢复命令执行；日常对象核查与查询通过页面完成。

## 2. 系统结构与目录

采用浏览器—Django—PostgreSQL/PostGIS 的单机结构。HTML 模板由 Django 输出；Bootstrap、ECharts、MapLibre 和 PMTiles 资源在本地提供。地图与图表在相应业务页面使用，基础页面不下载多余图表脚本。无独立 Node 应用服务、队列、容器或 GIS 全局环境重建。

## 3. 来源语义与设计证据

### 3.1 已核验的关联键

2025 年 1 月样本含 6,482 起事故、12,830 条车辆记录、22,165 条人员记录，三类来源主键分别唯一。6,482 起事故都有关联车辆；29 起没有人员明细。20,958 条人员记录带车辆引用，全部匹配车辆 `unique_id`，跨事故不一致为 0；匹配车辆 `vehicle_id` UUID 的数量为 0。该样本结论不能替代全量关系核验。

| 来源字段 | 含义与落地 |
|---|---|
| Crashes `collision_id` | 事故来源主键 → Collision.source_record_id |
| Vehicles `unique_id` | 车辆来源主键 → Vehicle.source_record_id |
| Vehicles `collision_id` | 查找事故来源主键后映射内部 collision_id；找不到时保留原键且关联为空 |
| Vehicles `vehicle_id` | 来源车辆 UUID → source_vehicle_uuid，不能与内部主键混用 |
| Person `unique_id` | 人员来源主键 → Person.source_record_id |
| Person `vehicle_id` | 查找 Vehicles.unique_id → 内部 vehicle_id；原引用另存 source_vehicle_id |
| Person `person_id` | 来源统计记录 UUID → source_person_uuid，不是身份证件 |

来源元数据中“匹配事故 unique_id”的描述与实际 Crashes 字段名存在历史命名差异，应使用实际字段 `collision_id`。Crashes 的 1—5 号车辆因素/车型槽位只表明该事故来源中的位置，不能据此按车辆表顺序猜配车辆。将这些槽位拆到 CollisionFactor，保留 slot；车辆、人员各自的因素拆到自己的关联表。

既有事故/车辆/人员 CSV 只选择了部分字段，因此不能从这些文件推导完整字段字典。设计结合官方元数据包含全部所需属性；正式五年全字段快照已通过分页获取，后续数量和质量验收见[数据导入与质量规则](数据导入与质量规则.md)及快照质量核对。

### 3.2 流量与空间

现有五年采样文件共 427,139 行；以“请求、路段、方向、日期、时刻”为候选键仍有 5,146 个流量值冲突组。业务观测表不把该组合设为唯一键。冲突组独立管理，成员记录分别保留；未解决冲突不计入可靠暴露量。观察值 0 是实际观测；未观测时段没有观测行，不能补成 0。

道路设计使用 NYC DCP ArcGIS 服务的 5 条道路及 5 条节点小样本，保留服务元数据和来源说明。这不是全市正式快照。路段中存在带前导零的 `SegmentID`、`NodeIDFrom`、`NodeIDTo`，原始载荷按来源保存；正式 26b 档案的节点 NODEID 是整数，端点关系匹配采用数字编号的规范字符串。以网络版本与来源要素编号为路段唯一键，不提前假设 SegmentID 在所有视图/版本中唯一。正式选用官方静态 LION 26b 档案，含 243,237 个道路要素和 139,674 个节点；版本内节点编号及道路档案 FID 经全量导入约束核对。

小样本的 SRID 为 102718（EPSG 等价标识 2263），单位 US survey foot；点 (1010964.44697878, 241812.261403456) 经 pyproj 转换为约 (-73.903467, 40.830354)，落在纽约范围。数据库统一存储 EPSG:4326，距离采用 geography 米或明确的米制投影；不把经纬度或 2263 英尺直接当米。

流量字段说明将 segmentid 定义为 LION 14 的编号。新网络编号必须经版本映射与几何核查，不能直接等同。全量空间对照支持流量 WKT 使用 EPSG:2263（US survey foot），转换到 4326 后与来源经纬度核对；官方字段说明未直接标注 EPSG，这一来源限制仍保留。节点也不都是真实交叉路口，`is_intersection` 可空，分类方法单独记录。

## 4. 四层数据及规范化

1. **不可变来源证据**：DataSource → Snapshot → StagedRecord。保留原始文件、捕获时间、来源版本、字段清单、范围、来源数量及逐行载荷。原始载荷与行身份由数据库触发器禁止修改/删除，处置状态可以更新。
2. **导入与质量过程**：ImportBatch 记录尝试、检查点、状态及计数；QualityIssue 记录问题及有依据的处置。重试复用快照与逐行身份，不重复创建原始证据。未经核验不得标为已发布。
3. **当前业务状态**：来源记录映射内部 bigint 主键。事故/车辆/人员持有可空关联，保留未解析原键。人工修正更新当前状态并增加 revision，同一事务写 AuditEvent 和 FieldChange；原始证据保持不变。origin 区分官方、人工、演示。
4. **可版本化分析结果**：统计缓存、历史风险与预测回测已经持有范围、规则版本、数据版本及已计算结果；历史报告冻结确定结果，简报保留汇总输入、模型原文及编辑版本。JSON 用于确定的派生结构和计算上下文，不能将原始 JSON 暂存载荷作为常规统计查询事实表。

业务事实通常满足 3NF：实体字段描述其主键；重复因素及损伤位置拆为一对多表；请求与地点拆分；网络版本独立；字典名称集中管理。事故级伤亡是来源独立事实，不能强制等于人员明细聚合，不能因缺少人员明细清零。车辆类型等单值属性直接记录来源文本，本身不违反 3NF；后续可用版本化映射将原值归入统一类别。

raw_record 与 source/source_record_id 的并存是追溯及自然键去重需要的有限冗余；已实现的导入服务校验原始行快照来源、来源键与实体种类，批量更新保留这一校验，并由外键和唯一约束共同保护。

地理匹配、预测参数和质量状态属于派生/管理信息，不覆盖来源字段。来源 JSON 与规则参数 JSON 是边界载荷；事故时间、关系、计数、几何、筛选字段均使用类型化关系字段。

## 5. 当前物理模型、完整性与事务

已经迁移 46 张项目关系表，另有 Django 认证、权限、会话及迁移表。AccessPolicy 仅承载内容类型和权限定义，不创建物理业务表。全部字段及约束由[数据字典](数据字典.md)列出。

完整性分层如下：

- 实体完整性：内部主键、来源+来源键唯一、快照行号唯一；快照非空文件摘要可去重。
- 参照完整性：来源、原始行、事故、车辆、网络、节点等均为真实外键，默认 PROTECT。人员—车辆额外使用组合外键，保证人员与车辆属于同起事故；路段端点必须属于同网络版本；观测冲突组必须属于同地点和时段。
- 业务检查：计数非负；缺失计数为 NULL；年龄有效值 0—130；因素槽位范围；来源官方记录要求证据引用；批次分类计数和不超过总数；已处理质量问题要求依据、操作者和时间；15 分钟观测不接受任意分钟；冲突记录不能直接标为可靠观测。
- 空间检查：空间字段固定类型和 SRID；点为空以外必须在世界坐标范围内且非空；道路和行政区要求有效、非空几何。纽约地域范围、道路类别及空间匹配可靠性由后续来源校验处理，不以简单包围盒替代精确行政边界。
- 审计保护：AuditEvent 与 FieldChange 不可更新/删除；载荷字段严格限为许可的元数据。认证日志不记录密码、表单全文、连接字符串或模型响应。

事务原则：一个批量导入块内写暂存状态、实体、质量问题与检查点；失败回滚该块并在外层另记失败，已提交块可恢复。源行总数、接受/拒绝/待核查/跳过数量在任务结束时完整对账。人工修正、revision、关联变化和成功日志原子提交，失败说明在回滚后另行保存。导入／维护／分析均有实际 PostgreSQL 隔离测试；风险在一致快照内整批写入结果，失败不会保留部分目标结果。

## 6. 时间规则

来源事故/流量的日期和时刻按 `America/New_York` 理解。事故存储 local_date + 可空 local_time；服务器审计及可确定的事件 UTC 使用 timestamptz。数据库实例原时区不改，Django USE_TZ 开启，页面按纽约当地时间显示。

`resolve_wall_time` 对两个 fold 候选执行 UTC 往返核对：唯一有效 UTC → unique；两个不同有效 UTC → ambiguous；没有候选 → nonexistent；字段缺失 → missing。模糊、缺失及不存在时刻的 UTC 保持 NULL，不悄悄按电脑时区解释，也不任选一个重复小时。当地日期仍可用于有说明的日/月统计；无效日期原始行留在暂存与质量表，等待处理。

小时/日完整流量分母须按当地日历与夏令时定义，不能固定每一天都为 96 个唯一 15 分钟槽。重复小时无偏移资料时不能称为完整观测。时间解析、非法格式和全量异常数量将在正式导入时验证。

## 7. 索引与查询设计

| 查询 | 已建立/计划的支持 |
|---|---|
| 事故日期分页 | Collision(local_date,id)，稳定排序用日期+主键 |
| 行政区与日期筛选 | Collision(borough_id,local_date) |
| 事故详情中的车辆和人员 | 外键默认 B-tree；车型、人员类型及伤害状态索引 |
| 范围/周边对象 | 事故、行政区、节点、道路、采样地点 geom 的 GiST |
| 采样地点时序 | Observation(site_id,local_date,local_time) |
| 质量及任务筛选 | QualityIssue(status,code)、原始行(snapshot,disposition) |
| 来源和重复识别 | source/source_record_id 与 snapshot/row_number 唯一索引 |
| 操作追溯 | AuditEvent(actor_id,created_at DESC)、(object_type,object_id) |

索引针对查询范围建立。已对全量来源键查询及工作台计数执行计划进行实测；批量发布后主动 ANALYZE，防止快照状态分布的旧估计导致大量嵌套索引探测。分区、汇总缓存或物化视图仍根据具体统计查询的实测结果决定，不将单次结果泛化为统一响应时间。

参数化空间 SQL 示例：

```python
with connection.cursor() as cursor:
    cursor.execute('''
        SELECT id FROM collisions_collision
        WHERE geom && ST_MakeEnvelope(%s,%s,%s,%s,4326)
          AND local_date >= %s AND local_date < %s
        ORDER BY local_date, id LIMIT %s
    ''', [west,south,east,north,start_date,end_exclusive,limit])
```

上界与 limit 必须由应用校验。动态排序字段从许可映射选择，不能拼接用户 SQL。事故级统计从 Collision 计算；用 EXISTS 筛选相关车辆/人员，或先分组再连接，避免一对多乘法重复统计事故和伤亡。

| ReportSnapshot | 当前物理表；bigint；report→Report、snapshot→Snapshot | (report,snapshot) 唯一，不可变；仅运行中报告可追加 |
| ExportJob | 当前物理表；UUID；owner、kind、format、report 可空外键、conditions、metadata、row_count、file_size、relative_path、状态与时间 | 成功任务不可变；报告归属一致；只发布完整文件 |
| AIBrief | 当前物理表；UUID；report/owner、provider、model、endpoint、prompt_version、input_summary、fingerprint、raw_text、generated_text、edited_text、revision、状态与时间 | 同报告同输入可复用；成功后仅可追加编辑版本，模型原文与输入不能覆盖 |
| AIRequest | 当前物理表；bigint；brief、attempt、status、error_code、http_status、prompt_tokens、completion_tokens、elapsed_ms、时间 | (brief,attempt) 唯一；成功或失败尝试均不可改写，不存密钥或响应头 |
| BriefRevision | 当前物理表；bigint；brief、number、actor、text、created_at | (brief,number) 唯一；不可变；作者须为简报所有者 |
| MaintenanceRun | 当前物理表；UUID；actor、operation、source_run 可空自引用、target_label、artifact_relative_path、status、summary、error_code、started_at/finished_at | 结束记录不可变；backup 不引用来源，restore 引用已完成备份；受控工具只创建新的隔离库 |

规则接口：输入规范化 conditions、data_revision、rule_version；输出值、单位、覆盖、质量、支持记录定位条件。风险、预测和报告复用同一指标服务，不能各自复制口径。风险分值不是事故概率。预测使用时序回测和朴素基线，参数只来自预测时点之前。AI 仅接收确定汇总，不能连接任意 SQL、修改事实或虚构原因。

## 9. 权限、配置和测试隔离

三个业务角色使用 Django Group/Permission，用户不因此成为数据库超级用户或 Django superuser。公共 `require_capability` 装饰器在每次请求检查权限；菜单与权限一致，但隐藏菜单不构成安全边界。账户管理与维护操作同时通过服务层重复校验。

| 能力 | 管理员 | 维护人员 | 分析用户 |
|---|---|---|---|
| 工作台、来源、查询分析、报告权限 | 是 | 是 | 是 |
| 批次查看、业务维护权限 | 是 | 是 | 否 |
| 账户管理、全局日志、系统配置权限 | 是 | 否 | 否 |

本地 `.env` 与密码文件只由服务端读取；示例文件含占位值。账户随机密码仅写私有交接凭据文件，不出现在页面或报告中。认证使用 Django 密码哈希、CSRF、HttpOnly 会话、同站点 Cookie、POST 退出；单进程登录尝试按客户端短期限流。当前本地 HTTP 不启用 HTTPS 专用 Cookie 标志；不据此声称适于公网部署。管理员不得向普通应用账户授予 CREATEDB 以省略测试初始化。

管理员预建 `test_nk_traffic` 并启用 PostGIS，归属普通应用账户；业务库与测试库名称必须不同。Django 测试入口要求 `--keepdb`；pytest 使用 `config.test_settings` 和 `--reuse-db`，在测试框架启动前就指向测试库。运行时再次查询 current_database 确认目标。迁移在独立空库首次重放，之后复用；测试使用事务回滚，不导入业务库样本。

数据库层的证据保护防止普通 DML 误改，不将拥有建表权限的应用角色描述为不可篡改的审计系统。DDL 权限隔离及高强度安全运维不是单机课程系统的验收承诺。

## 13. 业务维护与任务实现

业务维护引入 SavedQuery、CategoryMapping、DataRevision、ImportJob 四张物理表；连同空间、统计风险和预测结构，当前共 46 张项目表。详见[数据字典](数据字典.md)、[维护 E-R 图](diagrams/08_maintenance_er.svg)和[维护数据流图](diagrams/09_maintenance_dfd.svg)。事故、车辆、人员和流量实体增加 review_note，质量问题增加 revision。

- 查询表达版本 1：日期、区域、来源、状态、来源编号、属性条件与排序经同一 QueryForm 规范化；SavedQuery 使用 owner 隔离及有效名称条件唯一。保存入口验证签名条件和所有者，载入时重新校验表达。
- 业务服务以原始证据为参照维护当前实体；select_for_update 配合 revision 拒绝过期提交。失效保留外键并按事故—车辆—人员级联；恢复要求父对象有效。人工/演示新增不能指定官方来源。
- 维护事务与导入共享 PostgreSQL advisory lock (20261004, 2)，避免半途中入库与人工修订相互覆盖。成功事务追加 AuditEvent、FieldChange 和 DataRevision，失败响应只记录受控的错误类别，不保存原表单或凭据。
- CategoryMapping 采用内容不可变的版本行和唯一有效版本；来源稳定身份与行政区边界不通过元信息表单修改。
- ImportJob 将上传文件校验与导入分开排队。工作进程持会话级排他锁，使用短事务及 SKIP LOCKED 领取任务，重处理权限变化和进程遗留状态。任务阶段、进度及可读错误由 JSON 状态接口提供；大规模转换不进入 Web 请求。
- 账户维护串行校验最后一个启用管理员；维护操作不提供 is_staff / is_superuser 写入口。质量处理状态与流量统计资格独立。
- 工作台计数按快照状态和 DataRevision 水位缓存 60 秒。所有来源快照均已发布的域直接统计主业务表，避免不必要的百万行连接；存在未发布快照时仍执行发布状态过滤。该缓存不保存分析结果，后续聚合模块仍按其独立版本策略设计。

操作流程与边界详见[业务操作与维护](业务操作与维护.md)。

## 15. 统计与风险的实际实现

新增五张统计风险表，物理结构见[统计风险 E-R 图](diagrams/11_analytics_er.svg)，方法和操作见[统计与历史风险评价](统计与历史风险评价.md)。事故母集合以统一条件产生，车辆／人员独立汇总，事故因素按事故去重。时间／区域统计不依赖空间匹配，空间子集才核验当前关联资格。

统计和对比缓存以一致快照中的数据版本判断命中。发布、业务修订及引擎更换均改变版本；规则 ID 固定在风险查询和计算记录中。后台分析工作进程通过会话锁保证单实例，领取任务使用短事务及 SKIP LOCKED；计算持共享维护锁并一次提交规则引用、确定计数、归一化贡献和结果。导入／修订持相应排他锁，避免混合数据版本。

成功 RiskRun 和 RiskResult 不覆盖；数据版本不同则标示历史结果，关闭把当前明细当作旧支撑的入口。新规则与重算均新建记录。统计／对比／风险的个人查询采用表达版本 2，原档案查询版本 1 继续可用。当前未存储每次计算的完整业务事实副本，历史证据由聚合结果、来源快照和修订记录共同说明。

实际全量聚合与查询计划支持保留现有时间、外键和空间索引并使用版本缓存；未额外建立重型统计物化表。性能数字、SQL 计划和验收证据维护在阶段记录中，正式规则不绑定单次机器耗时。

## 16. 预测、回测与历史异常的实际实现

四张预测表的关系见[预测回测 E-R 图](diagrams/04_analysis_er.svg)，完整方法与操作见[统计预测与回测](统计预测与回测.md)。预测复用综合统计的官方事故母集合、来源覆盖、空间关联资格与版本接口。月／周日历序列保留缺失和部分周期，不插值；连续完整尾段满足门槛时才比较方法并外推。

规则代码 `count-forecast` 与 `historical-intensity` 分离。后台分析进程同时调度风险与预测，领取使用短事务及 SKIP LOCKED；预测计算持一致快照与共享维护锁，历史、回测、异常及未来结果一次提交。算法与数据库日期约束共同防止回测读入目标之后的数据。任务失败回滚子结果，并提供受控失败状态。

参数比较段先确定算法参数，独立评估段只滚动扩大已观测历史，冻结参数。基线、移动平均和指数平滑使用相同原点集合；逐步长和全部步长分别显示误差。未来经验参考带按对应步长的历史绝对误差构造，样本不足留空；不声称已验证未来覆盖概率。

成功记录及子证据不可变；新数据或引擎版本使旧记录显示历史提示并暂停当前明细入口，重算保留旧记录。预测查询使用 SavedQuery 表达版本 2，仅保存条件，私人所有权与签名校验沿用既有机制。预测不会修改事故事实，也不调用模型 API。


## 17. 报告、导出与模型简报的实际实现

六张报告表使项目物理表增至 45 张。统计／对比／流量在可重复读事务中生成并冻结；风险／预测引用不可变子结果，另存规则副本。ReportSnapshot 关联该数据版本的来源，data_version 保存来源状态集合及修订水位，不能伪造为单一外键。历史页面不重算旧结果。

报告和导出与风险／预测复用单实例分析进程；领取使用行锁跳过已锁任务，计算复用共享维护锁，每用户同类任务限一个待处理项。导出迭代全部记录，CSV 分卷、Excel 分表，完整写入并核对行数后发布。失败清理只涉及该任务自建的临时文件；已有同名文件不被删除。保存附件路径由 UUID 决定，下载再次校验所有者及范围。

AI 后端经受控 HTTPS 地址调用指定模型；网络等待不占业务数据库事务。输入只含冻结汇总及限制，输出通过结构和事实引用校验后保存。成功原文、请求尝试、用户编辑分别留存，失败重试受次数和时间窗口限制；服务重启将中断任务明确标为失败。同一报告的相同输入复用，不把另一报告的简报错误归属于当前报告。实际接口、打印及文件语义见[报表导出与 AI 简报](报表导出与AI简报.md)。

## 18. 运行维护与隔离验证的实际实现

MaintenanceRun 使项目表增至 46 张，运行日志与结构化核对结果进入普通管理模型。备份通过一致事务快照关联数据库归档与校验基线，文件采用允许目录清单及前后完整性检查。恢复只建新库，保留对象归属，核对表数、关系、空间与统计，并解包至独立文件目录。页面只查询结果，本地命令执行受控维护，结束证据由数据库保护。

已验证恢复编号可由启动器选择数据库和对应文件目录，私有运行配置仍由本机工程读取；独立的上传、导出和心跳目录避免副本写回主文件。业务检索使用单语句反连接排除未发布证据，在全部发布和部分发布状态下保留同一语义。方法及实际验证见[运行维护与综合验证](运行维护与综合验证.md)。
